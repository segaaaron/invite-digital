# Plan del evento y sus límites — Plan de implementación

> **Para agentes ejecutores:** REQUIRED SUB-SKILL: usa `superpowers:executing-plans`. Los pasos usan casillas (`- [ ]`).

**Objetivo:** que los tres planes que el sitio vende desde el ciclo 1 signifiquen algo — que sus límites se apliquen de verdad y que el atelier los vea venir antes de chocar.

**Arquitectura:** módulo nuevo `src/modules/plans/`. Columnas de límite en `plans`, `plan_id` en `events`, y una tabla de solicitudes de cambio. **Los módulos que aplican un límite reciben la capacidad ya resuelta; no importan el módulo de planes.**

**Spec:** `docs/superpowers/specs/2026-08-21-planes-design.md`

## Restricciones globales

Las mismas del plan del check-in (`docs/superpowers/plans/2026-08-21-checkin-qr.md`). **Aplican todas.** Las críticas aquí:

- Prefijo: `DATABASE_URL=postgres://invite:invite@localhost:5434/invite SITE_URL=http://localhost:3000`
- `domain` puro; `application` nunca importa `infrastructure`.
- **`guests`, `venue`, `registry` y `checkin` NO pueden importar `plans`.** Reciben la capacidad como argumento. Si `verify:boundaries` o el sentido común te empujan a importarlo, es que la firma está mal.
- Toda acción del panel abre con `await requireSession()`.
- Prohibido `any` y `@ts-ignore`.
- `pnpm typecheck && pnpm lint && pnpm test` en verde antes de cada commit.
- Las e2e locales necesitan `pnpm build` antes.

**Esta rebanada toca código cerrado desde la rebanada 1.** Después de cada tarea que lo haga, comprueba que **todas las pruebas previas siguen verdes** antes de commitear.

## Task 2: Dominio de la capacidad

**Archivos:** crear `src/modules/plans/domain/errors.ts`, `allowance.ts` y su test

**Produce:** `PlansError`, `plansError(kind, detail)`, `Allowance = { planSlug, maxGuestGroups: number | null, seating: boolean, registry: boolean, checkin: boolean }`, `canAddGroup`, `remainingGroups`, `hasFeature`

`PlansErrorKind = 'plan_limit_reached' | 'feature_not_included' | 'request_already_pending' | 'same_plan' | 'already_resolved' | 'not_found' | 'storage_failure'`

- [ ] **Paso 1: prueba que falla**

```ts
describe('canAddGroup', () => {
  it('sin límite siempre se puede', () => expect(canAddGroup(null, 9999)).toBe(true))
  it('por debajo del límite se puede', () => expect(canAddGroup(30, 29)).toBe(true))
  it('justo en el límite ya NO se puede', () => expect(canAddGroup(30, 30)).toBe(false))
  it('por encima tampoco', () => expect(canAddGroup(30, 31)).toBe(false))
  it('con límite cero no se puede ninguno', () => expect(canAddGroup(0, 0)).toBe(false))
})

describe('remainingGroups', () => {
  it('sin límite devuelve null, no infinito', () => expect(remainingGroups(null, 5)).toBeNull())
  it('cuenta lo que queda', () => expect(remainingGroups(30, 28)).toBe(2))
  it('nunca devuelve negativo', () => expect(remainingGroups(30, 35)).toBe(0))
})

describe('hasFeature', () => {
  it('respeta cada bandera', () => {
    const a = { planSlug: 'atelier', maxGuestGroups: 30, seating: true, registry: false, checkin: false }
    expect(hasFeature(a, 'seating')).toBe(true)
    expect(hasFeature(a, 'registry')).toBe(false)
  })
})
```

El caso «justo en el límite» es el que se escribe mal: con 30 de límite y 30 grupos ya creados, el siguiente hace 31 y no cabe.

- [ ] **Paso 2–5:** ciclo TDD y commit `feat: reglas de capacidad de un plan`

## Autorrevisión

**Cobertura:** §3 qué limita → 1, 2 · §4 dónde se aplica → 4, 5 · §5 aviso → 7 · §6 solicitudes → 6 · §7 esquema → 1 · §8 errores → 2, 4, 5, 6 · §9 pruebas → todas.

**El riesgo de esta rebanada es la regresión.** Las tareas 4 y 5 tocan cuatro módulos cerrados y fusionados. Cada una exige la suite previa en verde antes de commitear, y la 4 lleva además la instrucción explícita de entender cualquier prueba que se rompa antes de tocarla.

**La maqueta se conserva**, no se borra: es el diseño de referencia. Solo deja de estar
en `public/`, donde se servía sin sesión y podía confundirse con la aplicación real.

**El acoplamiento es la otra trampa.** Es tentador que `addGuestGroup` importe el módulo de planes y resuelva la capacidad él mismo. Ataría para siempre dos módulos que hoy son independientes, por una regla comercial que cambiará. La capacidad entra como argumento, y quien la resuelve es la acción, que ya vive en la frontera.
