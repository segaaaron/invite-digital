# Mesa de regalos y fondos en efectivo — Plan de implementación

> **Para agentes ejecutores:** REQUIRED SUB-SKILL: usa `superpowers:executing-plans`. Los pasos usan casillas (`- [ ]`).

**Objetivo:** que la pareja publique qué necesita, que el invitado reserve un regalo desde su propia invitación, y que la pareja lleve la cuenta de los fondos en efectivo.

**Arquitectura:** módulo nuevo `src/modules/registry/`, misma disposición que `src/modules/checkin/` y `src/modules/venue/`. Tres tablas nuevas. Escritura del invitado autorizada por token, no por sesión.

**Spec:** `docs/superpowers/specs/2026-08-21-regalos-design.md`

## Restricciones globales

Las mismas del plan del check-in (`docs/superpowers/plans/2026-08-21-checkin-qr.md`, sección «Restricciones globales»). **Aplican todas.** Las que más se olvidan aquí:

- Prefijo obligatorio: `DATABASE_URL=postgres://invite:invite@localhost:5434/invite SITE_URL=http://localhost:3000`
- `domain` puro; `application` nunca importa `infrastructure`; solo `src/app` los une.
- Ningún hexadecimal fuera de `src/shared/design/tokens.css`.
- Acciones del panel: `await requireSession()`. Acciones del invitado: **por token**, nunca sesión.
- Token desconocido o revocado → 404, nunca 403.
- Prohibido `any` y `@ts-ignore`. Errores con `Result`.
- `pnpm typecheck && pnpm lint && pnpm test` en verde antes de cada commit.

**Dos plantillas:** `src/modules/checkin/` para la forma del módulo. `src/modules/rsvp/` para el camino del invitado autorizado por token — **léelo antes de la Task 7**, porque ahí está resuelto el guardián que hay que reutilizar, no reinventar.

**La regla del dinero:** todo importe es un **entero en centavos**. Si en algún momento escribes un `float` para dinero, has introducido un descuadre que nadie podrá arreglar después.

```sql
CREATE TABLE gifts (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  event_id uuid NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  name varchar(160) NOT NULL,
  price_cents integer NOT NULL CHECK (price_cents > 0),

  url text,

  claimed_by_group_id uuid REFERENCES guest_groups(id) ON DELETE SET NULL,
  claimed_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX gifts_event_idx ON gifts (event_id);

CREATE TABLE gift_funds (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  event_id uuid NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  name varchar(160) NOT NULL,
  description text,
  goal_cents integer NOT NULL CHECK (goal_cents > 0),
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX gift_funds_event_idx ON gift_funds (event_id);

CREATE TABLE fund_contributions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  fund_id uuid NOT NULL REFERENCES gift_funds(id) ON DELETE CASCADE,
  guest_group_id uuid REFERENCES guest_groups(id) ON DELETE SET NULL,
  display_name varchar(160) NOT NULL,
  amount_cents integer NOT NULL CHECK (amount_cents > 0),
  method varchar(16) NOT NULL,
  message text,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX fund_contributions_fund_idx ON fund_contributions (fund_id);
```

`claimed_by_group_id` con `SET NULL`: borrar un grupo no puede borrar el regalo de la lista. En `fund_contributions` igual — el importe entregado sigue siendo cierto aunque el grupo desaparezca.

## Task 2: El dinero

**Produce:** `RegistryError`, `registryError(kind, detail)`, `parseAmount(text): Result<number, RegistryError>`, `formatAmount(cents, currency): string`

`RegistryErrorKind = 'invalid_amount' | 'invalid_name' | 'invalid_url' | 'already_claimed' | 'not_yours' | 'already_purchased' | 'wrong_event' | 'not_found' | 'storage_failure'`

- [ ] **Paso 1: prueba que falla**

```ts

  it('acepta el formato con coma decimal', () => expect(unwrap(parseAmount('1.234,50'))).toBe(123450))
  it('acepta el formato con punto decimal', () => expect(unwrap(parseAmount('1234.50'))).toBe(123450))
  it('acepta un entero', () => expect(unwrap(parseAmount('150'))).toBe(15000))
  it('acepta un decimal suelto', () => expect(unwrap(parseAmount('0,50'))).toBe(50))
  it('rechaza cero: un regalo de cero no es un regalo', () => expect(isErr(parseAmount('0'))).toBe(true))
  it('rechaza negativos', () => expect(isErr(parseAmount('-10'))).toBe(true))
  it('rechaza tres decimales', () => expect(isErr(parseAmount('10,555'))).toBe(true))
  it('rechaza texto', () => expect(isErr(parseAmount('mucho dinero'))).toBe(true))
  it('rechaza vacío', () => expect(isErr(parseAmount('  '))).toBe(true))
})

describe('formatAmount', () => {
  it('formatea en la moneda del evento', () => expect(formatAmount(123450, 'BOB')).toContain('1.234,50'))
  it('no pierde céntimos', () => expect(formatAmount(1, 'BOB')).toContain('0,01'))

```

- [ ] **Paso 2:** ejecutar → FALLA
- [ ] **Paso 3:** implementar. **Nada de `parseFloat` sobre el importe completo:** separa la parte entera de la decimal como cadenas y compón el entero. `parseFloat('1234.50') * 100` da `123449.99999999999` en algunos casos y redondearlo es tapar el problema, no resolverlo.

## Autorrevisión

**Cobertura:** §3 dinero → 2 · §4.1 regalo → 3 · §4.2 fondo → 4 · §5 carrera → 6, 7 · §6 rutas → 8, 10, 12 · §7 retención → 11 · §8 errores → 3, 5, 6 · §9 pruebas → todas.

**Los dos puntos donde esto se rompe de verdad:**

1. **La carrera** (Task 7). Un `SELECT` seguido de un `UPDATE` deja pasar dos reservas del mismo regalo, y el fallo solo aparece con dos invitados a la vez — nunca en desarrollo. La prueba con `Promise.all` es la única que lo demuestra.
2. **El dinero en coma flotante** (Task 2). Un descuadre de céntimos no tiene arreglo después, porque los datos ya están mal escritos.

**Consistencia de tipos:** `Gift`, `GiftStatus`, `Fund`, `Contribution` y `RegistryError` se usan con la misma forma en todas las tareas.
