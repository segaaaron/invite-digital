# Libro de firmas — Plan de implementación

> **Para agentes ejecutores:** REQUIRED SUB-SKILL: usa `superpowers:executing-plans`. Los pasos usan casillas (`- [ ]`).

**Objetivo:** desenterrar los mensajes que los invitados ya escriben al confirmar, y darles leído, destacado y respuesta.

**Arquitectura:** módulo nuevo `src/modules/guestbook/`. **Una sola tabla nueva**, `message_notes`, con el estado editable. El texto del mensaje no se copia: se lee de `rsvp_responses.message`, donde ya vive.

**Spec:** `docs/superpowers/specs/2026-08-21-mensajes-design.md`

## Restricciones globales

Las mismas del plan del check-in (`docs/superpowers/plans/2026-08-21-checkin-qr.md`, sección «Restricciones globales»). **Aplican todas.** Recordatorio de las que más se olvidan:

- Prefijo: `DATABASE_URL=postgres://invite:invite@localhost:5434/invite SITE_URL=http://localhost:3000`
- `domain` puro; `application` nunca importa `infrastructure`; solo `src/app` los une.
- Ningún hexadecimal fuera de `src/shared/design/tokens.css`.
- Toda acción abre con `await requireSession()`. **Esta rebanada no crea ninguna acción del invitado.**
- Prohibido `any` y `@ts-ignore`. Errores con `Result`.
- `pnpm typecheck && pnpm lint && pnpm test` en verde antes de cada commit.
- **Las e2e locales necesitan `pnpm build` antes.** `playwright.config.ts` solo construye en CI; una ruta nueva da 404 hasta reconstruir.

**Plantillas:** `src/modules/checkin/` y `src/modules/venue/` para la forma del módulo.

**La regla que estructura esta rebanada:** el texto del mensaje **no se copia a ninguna tabla nueva**. Si en algún momento escribes un `INSERT` que guarda el cuerpo del mensaje, has creado dos versiones del mismo texto que se desincronizarán.

```sql
CREATE TABLE message_notes (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  rsvp_response_id uuid NOT NULL UNIQUE REFERENCES rsvp_responses(id) ON DELETE CASCADE,
  read_at timestamptz,
  featured_at timestamptz,
  reply text,
  replied_at timestamptz
);
CREATE INDEX message_notes_featured_idx ON message_notes (featured_at) WHERE featured_at IS NOT NULL;
```

**Produce:** `GuestMessage`, `InboxFilter = 'all' | 'unread' | 'featured'`, `filterMessages(messages, filter)`, `unreadCount(messages)`

- [ ] **Paso 1: prueba que falla** — cubre:

## Task 4: Puertos y casos de uso

**Archivos:** crear `src/modules/guestbook/application/ports.ts`, `guestbook-use-cases.ts` y su test

**Produce:** `GuestbookRepository { listMessages(eventId), findResponseEvent(responseId), upsertNote(responseId, patch) }`, `listGuestbook`, `markRead`, `toggleFeatured`, `replyToMessage`

- [ ] **Paso 1: prueba que falla** — cubre:
  - `listGuestbook` compone mensaje + nota y **excluye las respuestas de RSVP sin mensaje** (confirmar sin escribir nada no es una firma del libro);
  - **un grupo con dos respuestas produce dos mensajes** — dijo dos cosas distintas en dos momentos;
  - `markRead` es **idempotente**: llamarlo dos veces no falla ni duplica;
  - `toggleFeatured` alterna en los dos sentidos;
  - `replyToMessage` sobre un mensaje ya respondido **sustituye** la respuesta anterior;
  - una respuesta de otro evento da `wrong_event`;
  - un `responseId` inexistente da `not_found`.
- [ ] **Paso 2–5:** ciclo TDD y commit `feat: leer, destacar y responder mensajes`

## Task 5: Adaptador Drizzle

**Archivos:** crear `src/modules/guestbook/infrastructure/drizzle-guestbook-repository.ts` y su test

- [ ] **Paso 1: prueba que falla contra Postgres real** — cubre obligatoriamente:
  - `listMessages` hace `leftJoin` de `rsvp_responses` con `message_notes` y **devuelve los mensajes que aún no tienen nota** (si es `innerJoin`, ningún mensaje nuevo aparece jamás — es el fallo silencioso de esta rebanada);

## Autorrevisión

**Cobertura:** §3 no duplicar → 1, 5 · §4 dominio → 2, 3 · §5 esquema → 1 · §6 rutas → 6, 7 · §7 errores → 2, 4 · §8 pruebas → todas.

**El fallo silencioso de esta rebanada** está en la Task 5: si `listMessages` usa `innerJoin` en vez de `leftJoin`, solo aparecen los mensajes que ya tienen nota — es decir, **ninguno nuevo, nunca**. Todo compilaría, todas las demás pruebas pasarían, y la bandeja estaría permanentemente vacía sin un solo error. Por eso su prueba es obligatoria y explícita.

**Consistencia de tipos:** `GuestMessage`, `InboxFilter` y `GuestbookError` se usan con la misma forma en todas las tareas.
